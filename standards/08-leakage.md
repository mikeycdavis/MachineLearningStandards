# Standard 8 — Leakage

Leakage is the failure that rewards you for committing it. A leaking pipeline produces the best
numbers the project has ever seen, arrives at review with every metric improved, and collapses on
deployment for reasons nobody can reconstruct because the evaluation that would have caught it was
the thing that was compromised. What this standard prevents is not a bad score but a good one that
means nothing — and the reason it needs to be a standard rather than a habit is that the defect is
usually introduced by a line of code that reads as tidy.

Source: item 8 of [`artifacts/prompts/ml-standards-spec.md`](../artifacts/prompts/ml-standards-spec.md).

## Scope

Applies to every path by which information unavailable at prediction time can reach a model during
training: preprocessing fitted across a split, features derived from the future, duplicate records
spanning partitions, identifiers that encode the outcome, and joins against tables that hold
current rather than historical state. [Standard 9](09-target-leakage.md) takes the specific case
where the leaked information is the target itself; everything else is here.

Applicability is proposed by the `training-code` and `ml-footprint` triggers. It is not proposed by
the presence of a preprocessing import alone — a script that scales data for a visualisation is
not training anything, and declaring the rule not-applicable with that reason is correct.

R5 narrows further, to evaluation in which a pretrained artifact or a public benchmark takes part.
Its catalog entry therefore carries no trigger at all: `training-code` would fire on a project that
trains from scratch on private data, and `status` would report its correct not-applicable
declaration as drift. No trigger detects that condition, and none is invented for it: `scripts/standards.mjs` builds a
closed set of trigger signals, so a name outside that set would never fire, and a project using a
released checkpoint would be told that none of the rule's triggers had fired. That is a false
reassurance, which is the failure this repository exists to prevent. The condition is therefore
declared rather than detected. A project states applicability for
`leakage.pretraining-contamination-stated` in `project-policy.yml` with its reason, and carries the
condition in `revisitWhen`, so that acquiring a pretrained artifact or adopting a public benchmark
reopens the declaration instead of silently invalidating it.

## Requirements

### R1 — Transformations are fitted inside the training portion of each split

**Every transformation whose parameters are learned from data — scaling, encoding, imputation,
vectorisation, dimensionality reduction, target encoding, feature selection — MUST be fitted on
the training portion only, and applied unchanged to validation and test data.** In a
cross-validation procedure the fit happens inside each fold, as
[Standard 10](10-cross-validation.md) requires.

The quantity leaked by a global fit is small and is not the point. A mean computed over the whole
dataset tells the training process something about the held-out rows, and the estimate that follows
is no longer an estimate of performance on data the process has not seen. The magnitude varies; the
claim being made is false regardless.

The distinction is mechanical. This fits the scaler on everything, then splits:

```python
scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)
X_train, X_test, y_train, y_test = train_test_split(X_scaled, y, random_state=0)
model = LogisticRegression().fit(X_train, y_train)
score = model.score(X_test, y_test)
```

This splits first and fits the scaler only where it is entitled to look, using a pipeline so that
the same discipline applies automatically at inference:

```python
X_train, X_test, y_train, y_test = train_test_split(X, y, random_state=0)
pipeline = Pipeline([("scale", StandardScaler()), ("model", LogisticRegression())])
pipeline.fit(X_train, y_train)
score = pipeline.score(X_test, y_test)
```

The second form is preferred over a manual `fit` on `X_train` followed by `transform` on `X_test`,
because the pipeline is a single object that can be serialised and served, which is what makes R4
hold without anyone having to remember it.

### R2 — Duplicate and near-duplicate records do not span a split

**Records that are duplicates or near-duplicates of one another MUST NOT be distributed across
different partitions, and the deduplication rule applied MUST be recorded.** A model evaluated on a
row it has already memorised is not being evaluated.

Near-duplication is the harder half and the more common one: resubmitted forms, re-scraped pages,
sensor readings a second apart, records regenerated by an upstream retry. The rule that defines
"near" is a judgement, which is exactly why it must be written down under
[Standard 3](03-dataset-provenance.md) with its effect rather than applied silently.

### R3 — Identifiers and index-like columns are examined before use

**Columns that identify, order, or index records MUST be examined for their relationship to the
target before being used as features, and MUST NOT be included by default.** A row number that
correlates with the label because the dataset was sorted by outcome, an account identifier issued
in blocks by the process being predicted, a filename encoding the class — each is a real feature
to the model and a nonexistent one in production.

The examination is a human activity and produces a recorded conclusion, not a passing test.

### R4 — The training pipeline mirrors the inference pipeline

**The transformations applied at training time MUST be the same transformations, in the same order,
with the same fitted parameters, that will be applied at inference.** Training and serving that
diverge produce a model that is correct in neither, and the divergence is normally introduced by
reimplementation rather than by intent.

Serialising a single fitted pipeline and serving that object is the practical form of this
requirement; two implementations of the same preprocessing, in two languages or two repositories,
is the shape that fails. [Standard 23](23-inference-behavior.md) specifies the serving contract
this requirement must match.

### R5 — Prior exposure of the evaluation data is stated

**Where a pretrained artifact or a public benchmark takes part in evaluation, the record MUST state
what is known about the evaluation data's prior exposure, and MUST NOT describe the result as an
unbiased estimate of generalisation unless exclusion is supported by evidence.**

R1–R4 govern leakage this project's pipeline creates. This requirement governs leakage the project
inherits: evaluation data a model had already seen before the project acquired it, or a benchmark
whose answers have been selected against enough times that a good score partly records that
selection. Kapoor & Narayanan (2023) catalogue eight leakage types across 294 affected papers in 17
fields; the ones reached here are the ones no transformation in the project's own pipeline touched.

Three states are distinguishable, and the record says which holds:

- **Established overlap.** The evaluation data is known to appear in the artifact's training corpus,
  or the benchmark has been used repeatedly to choose among this project's candidates. The number
  may still be reported, with the overlap beside it. It is not an unbiased estimate, and calling it
  one is what this forbids.
- **Undetermined.** The corpus is undisclosed, or disclosed and too large to search. For
  closed-weight artifacts this is the normal case and it is an honest answer. It is not a licence
  for the stronger claim: an unbiased estimate is not established by the absence of a way to check.
- **Exclusion supported by evidence.** A documented decontamination step, an artifact whose corpus
  is disclosed and searchable, or an evaluation set constructed after the artifact's cut-off. Here
  the claim is available, and the evidence is what makes it available.

**No project is asked to prove a negative.** Establishing that evaluation data is absent from an
undisclosed web-scale corpus is a research problem, not a compliance task, and a requirement to do
it would be waived on every project that met it honestly. What is asked is a sentence saying which
of the three states holds, so the uncertainty sits where a reader can see it rather than inside a
number. [Standard 4](04-dataset-versioning.md) supplies the identifiers that make an exclusion claim
checkable later, and [Standard 25](25-model-limitations.md) is where an undetermined corpus reappears
as a stated limitation.

## Prohibitions

### P1 — Preprocessing sees only what prediction-time code will

Reproduced verbatim from the source:

> allow preprocessing to see information it should not see

The test is a counterfactual about the deployed system: could the code that will run at prediction
time have obtained this information at that moment? If not, and the training-time code used it, the
prohibition is engaged. This covers the fitted-parameter cases below and also the ones that are not
about fitting at all — a filter applied to the whole dataset using knowledge of the labels, a
feature selection step run before the split, an imputation value copied from a later analysis.

P1 and P2 are two source statements of one conceptual prohibition,
`leakage.no-preprocessing-leakage`. The first states the principle; the second names the concrete
operation it is most often violated by. They are hosted as separate headings because both appear in
the source and each must have a home, not because they are different rules — a violation of P2 is
a violation of P1.

### P2 — Fit transformations on training data only

Reproduced verbatim from the source:

> fit scalers/encoders/imputation globally before a split when that leaks information

The source's qualifier is load-bearing and is not an escape hatch. A global fit that leaks nothing
is possible — a transformation whose parameters come from a fixed external specification rather
than from the data, or an encoding of a closed category set defined before the dataset existed —
and those cases are outside the prohibition. What is inside it is the ordinary case: a scaler, an
encoder, or an imputer whose parameters are estimated from rows that include the held-out
partition.

Where the qualifier is claimed, the claim belongs in writing, because "this particular global fit
leaks nothing" is precisely the sentence a leaking pipeline is defended with.

## Evidence and verification

| Rule | What demonstrates compliance | How it is verified | Assurance |
|---|---|---|---|
| R1 | A pipeline object fitted after the split, or an explicit fit on the training partition with transform applied elsewhere | Detector A1, plus manual review | Partial — an in-file ordering is evidence, never proof |
| R2 | The deduplication rule and its effect recorded with the dataset, per [Standard 3](03-dataset-provenance.md) | Manual review | None — reports `not-evaluated` |
| R3 | A recorded examination of each identifier and index-like column with its conclusion | Manual review | None — `not-evaluated` |
| R4 | One serialised fitted pipeline used in both paths, or a documented equivalence between two implementations | Manual review | None — `not-evaluated` |
| R5 | A recorded statement of prior exposure naming which of the three states holds, and the evidence where exclusion is claimed | Manual review | None — `not-evaluated` |
| P1, P2 | Attestation that no transformation was fitted over data the inference path could not see, supported by A1 finding nothing | Detector A1: per Python file, a preprocessing `.fit(` or `.fit_transform(` (StandardScaler, MinMaxScaler, OneHotEncoder, SimpleImputer, TfidfVectorizer, PCA) appearing before `train_test_split(`, `KFold(`, `TimeSeriesSplit(`, `GroupKFold(`, or `StratifiedKFold(` | Partial — warning when it fires; a clean run reports `insufficient-evidence`, never a pass |

**What the automated check cannot establish.** Detector A1 reports a true fact — that within one
Python file, a preprocessing fit appears textually before a split call — and that fact is a proxy
for the one that matters, which is order in the dataflow. The proxy fails in both directions. It
over-reports when the variable being fitted is already a training subset loaded from disk, which is
compliant and looks identical. It under-reports whenever the fit and the split live in different
files, whenever the split is performed by a helper the detector does not recognise, and whenever
the code is a notebook whose cells were executed out of order — in which case the file's ordering
describes nothing at all. A run with no A1 finding therefore establishes that this one textual
pattern is absent and nothing about whether the pipeline leaks, which is why the rule reports
`insufficient-evidence` rather than passing.

## Additions this standard makes beyond the source

- R2's requirement that the deduplication rule be *recorded*, and the treatment of near-duplicates
  as the substantive case. The source names duplicate records spanning a split as a leakage path;
  the recording obligation and the near-duplicate discussion are this standard's additions.
- R3's rule that identifier and index-like columns are examined before use and not included by
  default. The source names identifiers that encode the outcome as a leakage path; making the
  examination a required, recorded step is this standard's structure.
- R4, the training-inference mirror. The source requires preprocessing to be fitted with the same
  discipline that will apply at inference; extending that to a requirement that the same fitted
  object be used, and naming reimplementation as the usual cause of divergence, is authored here.
- R5 in full. The source scopes leakage to what the project's own pipeline does; evaluation data
  already seen by an artifact the project did not train is outside every claim it makes. The three
  exposure states, and the decision to require a statement rather than an exclusion proof, are
  added here.
- The reading of P2's qualifier "when that leaks information" as a narrow, writable exemption
  covering externally specified parameters, together with the requirement that such a claim be
  recorded. The source supplies the qualifier and no guidance on it.
- The paired code fragments in R1 and the preference for a pipeline over a manual fit-and-transform
  pair. These are authored illustration, not source text.

## Relationship to other standards

[Standard 9](09-target-leakage.md) is the specific case of this standard where the leaked
information is the target. [Standard 6](06-temporal-splitting.md) governs the leakage path that
runs through time, and [Standard 7](07-feature-availability.md) describes the same defect observed
from the serving side. [Standard 10](10-cross-validation.md) restates R1 at fold granularity,
where the global fit is both easier to commit and harder to see.
[Standard 5](05-train-validation-test-separation.md) draws the boundary this standard defends,
and [Standard 17](17-feature-lineage.md) supplies the derivation records without which R1 and R3
are answered by reading code.

## Implementation

**Partially checked.** `standards scan` runs detector A1 over Python sources and reports a warning
where a preprocessing fit precedes a split call within the same file. The finding is real, cheap,
and frequently correct, and it is the sharpest automated check in this repository — which is a
statement about the rest of the catalog more than about A1.

Nothing establishes that a pipeline is free of leakage. Multi-file flows are not examined,
out-of-order notebooks are not proven clean, and the detector cannot see whether the data being
fitted is already a training subset. R2, R3, and R4 have no mechanism at all and report
`not-evaluated`; `leakage.no-preprocessing-leakage` reports `insufficient-evidence` when A1 is
silent, because a mechanism exists and its silence is not a result. The gap between "A1 found
nothing" and "this pipeline does not leak" is stated in the rule's assurance note for the same
reason [ADR 0004](../artifacts/adr/0004-honest-automation.md) requires one: a green result that is
read as verification is worse than no check.
