## What

`artifacts/catalog-baseline.json` carries `"frameworkVersion": "1.4.0"` while the rule data it
locks is the 2.0.0 catalog. Set it to `2.0.0`, so the field states the version the baseline was
actually reviewed at.

## Why

The field's meaning is established by its own history rather than by documentation, which is why
it was worth measuring before changing it. It has been set exactly four times, each in the commit
that carried the release changing the baseline: `1.0.0` at `13e6dbe`, `1.1.0` at `06feba7`,
`1.3.0` at `62f7426`, `1.4.0` at `6c4f8ea`. It records the framework version the baseline
corresponds to.

`a8d57c5` then changed the baseline's rule data for [[FE-34]] and left the field alone — correctly
at the time, because the carrying version did not exist to be named, which is the same reason that
commit put its reason in the `$comment` instead of `CHANGELOG.md`. `082ecba` supplied the version.
The field is now the last part of the baseline still naming a version the file no longer describes.

Nothing reads it: `scripts/integrity.mjs` compares rule entries and never opens the field, so no
gate is weakened and no verdict changes. That makes it cosmetic to a machine and not to a reader
— this is the human-reviewed artifact whose entire purpose is that catalog changes are visible and
reviewable, and a provenance field stating the wrong version in that file is the same class of
defect as the release claim `082ecba` retired two lines above it.

## Outcome

**`frameworkVersion` reads `2.0.0`, and nothing else in the file moved.** The diff is one
line. `npm run integrity` reports 53 locked and 53 live rules matching their reviewed baseline;
`npm test` is 301/301; the pipeline is 12/12. `reviewedOn` stays `2026-08-26` as scoped.

## Notes

**Deliberately deferred once already, and that was right.** `082ecba` left it under the precedent
set by `d440843`: a commit corrects the claim its own change falsified and leaves adjacent
staleness alone, because sweeping it in turns a reviewable correction into an unreviewable one.
This item is that separate pass.

**Scope boundary.** Change the value, nothing else. `reviewedOn` stays `2026-08-26`: this records
which version the review corresponds to, it does not re-perform the review. Whether anything
*should* read the field, and whether it should exist at all, are questions this item does not
answer and does not need to.

**Conflict to respect.** [[FE-24]] would edit this same file — any catalog addition forces a
baseline update via `scripts/integrity.mjs`, and a policy declaration via the parity assertion at
`test/policy.test.mjs:53`. The two must not run concurrently. FE-24 is blocked on decisions nobody
has taken, so the conflict is currently theoretical.
